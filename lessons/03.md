# Lesson 03 · Continuous delivery the old way: a bare server and Ansible

By the end of the lesson:

- Conduit runs on the class server, deployed by hand the old way;
- the same deploy is an Ansible playbook in your repository;
- a runner on the server deploys every green commit on `main` by itself;
- you rolled back a bad release.

Today you work on two machines. Your **laptop** (WSL) holds your clone and runs Ansible. The **class server** runs Conduit. The instructor writes the server address and your number N on the board. In the commands, `studentNN` is your user (for N = 7: `student07`) and `80NN` is your port (`8007`).

## Starting state

- Lesson 2 is finished: your fork has `.github/workflows/ci.yml` with `unit-tests` and `secret-scan`, and the last run on `main` is green.
- `ssh -T git@github.com` greets you by name. The class server trusts the same key.
- Your clone is in `~/devsecops-conduit` on the laptop.

## Log in

On the laptop:

```bash
ssh studentNN@SERVER
```

Replace `SERVER` with the address on the board. Type `yes` the first time.

Checkpoint: the prompt changes to `studentNN@class-server`.

> [!NOTE]
> The instructor never made a password for you. The server took your public key from `github.com/<your-name>.keys`, the same key you added in Lesson 2. Only the laptop with the private half can log in as you.

## Mission 1 · Look around (10 minutes)

On the server:

```bash
hostname
whoami
python3 --version
sudo -n true
ls /home
ls /home/student02
ls -l ~/.config/conduit/
```

What you should see:

- `sudo` says a password is required: you are not the administrator.
- `/home` lists every student, but you cannot open another student's folder. (If you are `student02`, try `student03`.)
- `secrets.env` has the rights `-rw-------`: only you can read it. It holds the password of your own database.

Do not print `secrets.env` on the screen, and never on the projector.

> [!NOTE]
> Many people share this server. Each has an account with only the rights it needs. If your account is broken into, the attacker is stuck inside it: no other folders, no other databases, no administrator.

## Mission 2 · Deploy by hand, the old way (30 minutes)

Do everything on the server. Use your GitHub username instead of `<you>`.

**1. Get the code and the libraries:**

```bash
cd ~
git clone https://github.com/<you>/devsecops-conduit.git by-hand
cd by-hand/backend
python3 -m venv ~/by-hand-venv
~/by-hand-venv/bin/pip install -r requirements.txt
```

The last command takes a few minutes, because the whole class downloads at the same time. Watch the list of libraries go by: all of them now land on this server.

**2. Load the settings and prepare the database:**

```bash
set -a
source ~/.config/conduit/secrets.env
set +a
~/by-hand-venv/bin/python -m alembic -c alembic.ini upgrade head
```

**3. Start the API on your port:**

```bash
~/by-hand-venv/bin/uvicorn conduit.app:app --host 0.0.0.0 --port 80NN
```

**4. Open it from the laptop.** In a second WSL terminal:

```bash
curl http://SERVER:80NN/api/health-check
```

Checkpoint: `{"success":true,"version":"0.1.0",...}`. Your API runs on a real server.

**5. Now press Ctrl+C** in the server terminal and run the `curl` again. The service is gone.

> [!NOTE]
> Think about the questions on the board. What happens when the server reboots? When you log out? When you are ill and a classmate must deploy? When there are ten servers? Which version is running right now? Who changed what, and when? The answer every time: somebody must remember and type everything again.

**6. Clean up:**

```bash
cd ~
rm -rf by-hand by-hand-venv
```

## Mission 3 · The same with Ansible (50 minutes)

Now you write the steps down once, as code, on the **laptop**.

**1. A branch:**

```bash
cd ~/devsecops-conduit
git switch main
git pull
git switch -c deploy/ansible
```

**2. Teach the health check which commit is running.** Open `backend/version.py` and make it look like this. Two lines are new, and the last line gets `"revision"`:

```python
import os

__status__ = True
__version__ = "0.1.0"
__message__ = "Conduit Realworld API"
__revision__ = os.getenv("APP_REVISION", "dev")

response = {"success": __status__, "version": __version__, "message": __message__, "revision": __revision__}
```

**3. The inventory: which server, which user.** Create `deploy/inventory.ini` with one line. Put in the server address, your user, your port and your GitHub username:

```ini
[conduit]
class-server ansible_host=SERVER ansible_user=studentNN app_port=80NN github_user=<you>
```

**4. The service: how the server runs the API.** Create `deploy/conduit.service.j2`:

```ini
[Unit]
Description=Conduit API

[Service]
WorkingDirectory={{ app_dir }}/src/backend
EnvironmentFile=%h/.config/conduit/secrets.env
Environment=APP_REVISION={{ code.after }}
ExecStartPre={{ app_dir }}/venv/bin/python -m alembic -c alembic.ini upgrade head
ExecStart={{ app_dir }}/venv/bin/uvicorn conduit.app:app --host 0.0.0.0 --port {{ app_port }}
Restart=on-failure

[Install]
WantedBy=default.target
```

These are the same commands as in Mission 2. The parts in `{{ }}` are filled in by Ansible. `Restart=on-failure` starts the API again if it crashes. `WantedBy=default.target` starts it after every reboot.

**5. The playbook: the steps.** Create `deploy/playbook.yml`. Spaces, not tabs:

```yaml
- name: Deploy the Conduit API
  hosts: conduit
  vars:
    revision: main
    app_dir: "{{ ansible_env.HOME }}/conduit"
    repo_url: "https://github.com/{{ github_user }}/devsecops-conduit.git"

  tasks:
    - name: Get the code of one exact commit
      ansible.builtin.git:
        repo: "{{ repo_url }}"
        dest: "{{ app_dir }}/src"
        version: "{{ revision }}"
        force: true
      register: code
      notify: Restart the API

    - name: Install the Python packages
      ansible.builtin.pip:
        requirements: "{{ app_dir }}/src/backend/requirements.txt"
        virtualenv: "{{ app_dir }}/venv"
        virtualenv_command: python3 -m venv
      notify: Restart the API

    - name: Create the folder for my services
      ansible.builtin.file:
        path: "{{ ansible_env.HOME }}/.config/systemd/user"
        state: directory
        mode: "0755"

    - name: Install the service
      ansible.builtin.template:
        src: conduit.service.j2
        dest: "{{ ansible_env.HOME }}/.config/systemd/user/conduit.service"
        mode: "0644"
      notify: Restart the API

    - name: Start the API now and after every reboot
      ansible.builtin.systemd_service:
        name: conduit
        scope: user
        state: started
        enabled: true
        daemon_reload: true

    - name: Restart now if anything changed
      ansible.builtin.meta: flush_handlers

    - name: Check that the API answers
      ansible.builtin.uri:
        url: "http://127.0.0.1:{{ app_port }}/api/health-check"
      register: health
      retries: 30
      delay: 1
      until: health.status == 200

    - name: Show the running version
      ansible.builtin.debug:
        msg: "{{ health.json }}"

  handlers:
    - name: Restart the API
      ansible.builtin.systemd_service:
        name: conduit
        scope: user
        state: restarted
        daemon_reload: true
```

Read it with the instructor. Each task has a name that says what it does. A task that changes something can **notify** the handler; the handler restarts the API only if something changed.

> [!NOTE]
> A script says “do this, then this”. A playbook says “make it so”. If the code is already at the right commit, Ansible does not touch it. That is called **idempotent**: you can run it any number of times, and the server ends up in the same state.

**6. Install Ansible on the laptop:**

```bash
source .venv/bin/activate
python -m pip install ansible-core
```

**7. Commit and push the branch**, so the server can download it:

```bash
git add backend/version.py deploy/
git commit -m "Deploy the API to the class server with Ansible"
git push -u origin deploy/ansible
```

**8. Deploy your branch:**

```bash
ansible-playbook -i deploy/inventory.ini deploy/playbook.yml -e revision=deploy/ansible
```

The first run installs everything and takes a few minutes. Checkpoint: the last task shows a `revision` that equals `git rev-parse HEAD`, and the summary line says `failed=0`.

**9. Run it again:**

```bash
ansible-playbook -i deploy/inventory.ini deploy/playbook.yml -e revision=deploy/ansible
```

Checkpoint: `changed=0`. Nothing needed to change.

**10. Check it the way a user would**, from the laptop:

```bash
curl http://SERVER:80NN/api/health-check
```

Then log out of the server with `exit`. Run the `curl` again: the API keeps running. It is now a service, not a program in your terminal.

**11. Merge.** Open a pull request in your fork (check the base repository). Two green checks, then merge. The playbook is code: it was reviewed like everything else.

## Mission 4 · A robot on the server (25 minutes)

> [!NOTE]
> GitHub is on the internet, the class server is inside the college network. GitHub cannot connect to it. The **runner** is a program on the server that connects out to GitHub and asks for work. No door is open from the internet, and GitHub keeps no key to the server.

**1. Close the door to strangers first.** In your fork open **Settings → Actions → General**. Under **Approval for running fork pull request workflows from contributors** choose **Require approval for all external contributors** and click **Save**.

> [!WARNING]
> A runner runs whatever the workflow asks, with the rights of its user. Your fork is public. Without approval, a stranger could open a pull request that tells your runner to do anything your account on the server can do.

**2. Get a registration token.** Open **Settings → Actions → Runners → New self-hosted runner**, choose **Linux** and **x64**. Scroll to the **Configure** section and copy only the token from the `./config.sh` line. It works for one hour.

**3. Install the runner on the server**, in your home folder:

```bash
mkdir ~/runner
cd ~/runner
tar xzf /opt/actions-runner/actions-runner-linux-x64-*.tar.gz
./config.sh --unattended --url https://github.com/<you>/devsecops-conduit --token TOKEN --name class-server --labels class-server
```

**4. Run it as your own service.** Create the file `~/.config/systemd/user/github-runner.service` with `nano`:

```ini
[Unit]
Description=GitHub Actions runner

[Service]
WorkingDirectory=%h/runner
ExecStart=%h/runner/run.sh
Restart=always

[Install]
WantedBy=default.target
```

```bash
systemctl --user daemon-reload
systemctl --user enable --now github-runner
systemctl --user status github-runner --no-pager
```

Checkpoint: the status says `active (running)`, and on GitHub **Settings → Actions → Runners** shows `class-server` as **Idle**.

## Mission 5 · The robot deploys (20 minutes)

**1. A branch on the laptop:**

```bash
git switch main
git pull
git switch -c ci/deploy
```

**2. Add a third job at the end of `.github/workflows/ci.yml`**, at the same indentation as `unit-tests`:

```yaml
  deploy:
    needs: [unit-tests, secret-scan]
    if: github.event_name == 'push'
    runs-on: [self-hosted, class-server]
    steps:
      - uses: actions/checkout@v7
      - name: Deploy this commit to the class server
        run: ansible-playbook -i deploy/inventory.ini deploy/playbook.yml -c local -e revision="$GITHUB_SHA"
```

Read it with the instructor:

- `needs` — the job waits for both checks. If one is red, nothing is deployed.
- `if` — only a push to `main` deploys. A pull request is only tested.
- `runs-on` — this job runs on your runner, on the class server.
- `-c local` — the same playbook, but the robot is already on the server, so it needs no SSH.
- `$GITHUB_SHA` — the exact commit this run is for.

**3. Commit, push, open a pull request:**

```bash
git add .github/workflows/ci.yml
git commit -m "Deploy every green commit on main to the class server"
git push -u origin ci/deploy
```

On the pull request, `deploy` shows as **skipped**. That is correct. Merge it.

**4. Watch the robot.** Open the **Actions** tab. On `main` the job `deploy` starts after the two checks and runs on `class-server`. Open its log: the same Ansible tasks you saw on the laptop.

Checkpoint: from the laptop,

```bash
git switch main
git pull
git rev-parse HEAD
curl http://SERVER:80NN/api/health-check
```

shows the same SHA twice. From now on, every merge goes live by itself.

## Mission 6 · A bad release and a rollback (15 minutes)

**1. Make a typo that the tests do not see.** On a new branch, open `backend/conduit/api/routes/health_check.py` and change the last line from `return response` to `return respons`.

```bash
git switch -c release/tidy-health
```

```bash
python -m pytest tests/unit -q
git add backend/conduit/api/routes/health_check.py
git commit -m "Tidy the health check"
git push -u origin release/tidy-health
```

The unit tests pass: `7 passed`. Open the pull request: two green checks. Merge it.

**2. Watch the deploy fail.** The job `deploy` retries the health check for 30 seconds and turns red. The `curl` now answers with an error. Production is down.

> [!NOTE]
> The unit tests never start the application, so they never call the health check. The last task of the playbook did. A green check proves only what the checks check.

**3. Roll back first.** In the **Actions** tab open the previous run on `main` that was green, click **Re-run jobs → Re-run all jobs**. It deploys its own commit again. Checkpoint: the `curl` answers with the previous SHA.

> [!NOTE]
> Users cannot work while you look for the bug. Bring back the version that worked, then fix calmly. Notice what the rollback had to do: fetch the old code again and check every library again, because the playbook overwrote the old version on the server. Keep this in mind for the next lesson.

**4. Fix `main` with a revert.** Open the merged pull request `release/tidy-health` and click **Revert**. Merge the new pull request. The robot deploys the fixed `main`. Checkpoint: the `curl` answers with the newest SHA.

## Troubleshooting

1. **`Permission denied (publickey)` on `ssh`.** The server knows the keys that were on your GitHub account when the instructor prepared it. Tell the instructor if you added a new key since then.
2. **`pip install` is slow.** The whole class downloads at once. Wait; do not restart it.
3. **`address already in use` on your port.** The program from Mission 2 still runs. Run `pkill -u $USER -f uvicorn`, then try again.
4. **Ansible: `Failed to connect to the host via ssh`.** First make `ssh studentNN@SERVER` work by hand. Then compare the address and the user in `inventory.ini`.
5. **Ansible: `Failed to connect to bus`.** Log out of the server, log in again, and repeat. If it stays, tell the instructor.
6. **The health check task fails after 30 retries.** On the server run `journalctl --user -u conduit -n 30 --no-pager` and read the last error.
7. **The deploy job says `Waiting for a runner to pick up this job`.** The runner is offline or has another label. On the server run `systemctl --user status github-runner --no-pager`; the label must be `class-server`.
8. **`./config.sh` says the token is invalid.** The token lives one hour. Get a new one from **New self-hosted runner**.
