# Lesson 03 · Continuous delivery the old way: your own server and Ansible

By the end of the lesson:

- you have your own Linux server on the internet;
- Conduit runs on it, first deployed by hand the old way;
- the same deploy is an Ansible playbook in your repository;
- a robot deploys every green commit on `main` by itself.

Today you work on two machines. Your **laptop** (WSL) holds your clone and runs Ansible. Your **server** runs Conduit. In the commands, replace `YOUR-IP` with the address of your server and `<you>` with your GitHub username.

## Starting state

- Your fork has `.github/workflows/ci.yml` with the jobs `unit-tests` and `secret-scan`, and the last run on `main` is green.
- `ssh -T git@github.com` greets you by name.
- Your clone is in `~/devsecops-conduit` on the laptop.

**Catch up, if your fork has no `ci.yml` with two jobs yet.** On a new branch, create `.github/workflows/ci.yml` with the text from **The complete ci.yml** at the end of [Lesson 02](02.md#the-complete-ciyml), open a pull request into **your own fork**, wait for two green checks and merge it.

## Mission 0 · Your own server (25 minutes)

Follow [Your own server in Azure](server-setup.md). It gives you a free Ubuntu server with your SSH key on it and port 8000 open.

Checkpoint: on your laptop, `ssh azureuser@YOUR-IP` logs you in, and `sudo whoami` answers `root`.

## Mission 1 · Look around (10 minutes)

On the server:

```bash
hostnamectl
whoami
sudo whoami
sudo ss -tlnp
sudo journalctl -u ssh --no-pager | grep -c "Invalid user"
```

What you should see:

- Ubuntu 24.04. You are `azureuser`, and `sudo` makes you `root`: this machine is yours.
- `ss` lists the programs that listen on the network. Only `sshd` on port 22 is open to the world.
- The last number counts strangers who tried to log in with made-up user names. It may still be 0 on a new server. Run it again at the end of the lesson.

> [!NOTE]
> Your server has a public address, and robots try every address on the internet all day. They guess passwords. Your server does not accept passwords at all, only your key, so the guesses fail.

## Mission 2 · Deploy by hand, the old way (35 minutes)

Do everything on the server.

**1. Install the database and the tools:**

```bash
sudo apt update
sudo apt install -y postgresql python3-venv git
```

**2. Create a database user and a database.** You type the password yourself:

```bash
sudo -u postgres psql -c "CREATE USER conduit WITH PASSWORD 'by-hand-password'"
sudo -u postgres createdb -O conduit conduit
```

**3. Get the code and the libraries:**

```bash
cd ~
git clone https://github.com/<you>/devsecops-conduit.git
cd devsecops-conduit/backend
python3 -m venv ~/venv
~/venv/bin/pip install -r requirements.txt
```

**4. Give the API its settings and prepare the database:**

```bash
export APP_ENV=prod SECRET_KEY=by-hand JWT_SECRET_KEY=by-hand
export POSTGRES_HOST=127.0.0.1 POSTGRES_PORT=5432 POSTGRES_DB=conduit
export POSTGRES_USER=conduit POSTGRES_PASSWORD=by-hand-password
~/venv/bin/python -m alembic -c alembic.ini upgrade head
```

**5. Start the API:**

```bash
~/venv/bin/uvicorn conduit.app:app --host 0.0.0.0 --port 8000
```

**6. Open it from the laptop.** In a second WSL terminal:

```bash
curl http://YOUR-IP:8000/api/health-check
```

Checkpoint: `{"success":true,"version":"0.1.0",...}`. Your API runs on a server on the internet.

**7. Now press Ctrl+C** in the server terminal and run the `curl` again. The service is gone.

> [!NOTE]
> Think about the questions on the board. What happens when the server reboots? When you close the terminal? Where is the database password now? (Run `history | tail`.) Which user runs the API, and what could an attacker do with it? Which version is running? Could a classmate repeat all this on a second server tonight?

**8. Clean up the hand-made parts:**

```bash
cd ~
rm -rf devsecops-conduit venv
history -c
```

## Mission 3 · The same with Ansible (40 minutes)

Now you write the steps down once, as code, on the **laptop**.

**1. A branch:**

```bash
cd ~/devsecops-conduit
git switch main
git pull
git switch -c deploy/ansible
```

**2. Teach the health check which commit is running.** Open `backend/version.py` and make it look like this. Two lines are new, and the last line gets `"revision"`:

```python
import os

__status__ = True
__version__ = "0.1.0"
__message__ = "Conduit Realworld API"
__revision__ = os.getenv("APP_REVISION", "dev")

response = {"success": __status__, "version": __version__, "message": __message__, "revision": __revision__}
```

**3. The inventory: which server.** Create `deploy/inventory.ini`:

```ini
[conduit]
server ansible_host=YOUR-IP ansible_user=azureuser

[conduit:vars]
github_user=<you>
ansible_ssh_common_args=-o UserKnownHostsFile=deploy/known_hosts -o StrictHostKeyChecking=yes
```

**4. Pin the identity of your server.** Save its public host key in the repository, then compare the fingerprint with the one the server itself reports:

```bash
ssh-keyscan -t ed25519 YOUR-IP > deploy/known_hosts
ssh-keygen -lf deploy/known_hosts
ssh azureuser@YOUR-IP ssh-keygen -lf /etc/ssh/ssh_host_ed25519_key.pub
```

Checkpoint: both lines show the same `SHA256:…`.

> [!NOTE]
> Your key proves to the server who you are. The host key proves to you which server it is. With the fingerprint saved in the repository, you and the robot refuse to talk to any machine that only pretends to be your server.

**5. The service: how the server runs the API.** Create `deploy/conduit.service.j2`:

```ini
[Unit]
Description=Conduit API
After=network.target postgresql.service

[Service]
User=conduit
WorkingDirectory=/opt/conduit/src/backend
EnvironmentFile=/etc/conduit/conduit.env
Environment=APP_REVISION={{ code.after }}
Environment=PYTHONDONTWRITEBYTECODE=1
ExecStartPre=/opt/conduit/venv/bin/python -m alembic -c alembic.ini upgrade head
ExecStart=/opt/conduit/venv/bin/uvicorn conduit.app:app --host 0.0.0.0 --port 8000
Restart=on-failure
NoNewPrivileges=true

[Install]
WantedBy=multi-user.target
```

These are the commands from Mission 2. `User=conduit` runs the API as a small user that can do nothing else. `Restart=on-failure` starts it again if it crashes. `WantedBy=multi-user.target` starts it after every reboot. The parts in `{{ }}` are filled in by Ansible.

**6. The playbook: the steps.** Create `deploy/playbook.yml`. Spaces, not tabs:

```yaml
- name: Deploy the Conduit API
  hosts: conduit
  become: true
  vars:
    revision: main
    repo_url: "https://github.com/{{ github_user }}/devsecops-conduit.git"

  tasks:
    - name: Install the system packages
      ansible.builtin.apt:
        name: [git, acl, python3-venv, python3-packaging, python3-psycopg2, postgresql]
        update_cache: true
        cache_valid_time: 3600

    - name: Create a user that can only run the API
      ansible.builtin.user:
        name: conduit
        system: true
        shell: /usr/sbin/nologin
        create_home: false

    - name: Create the folder for the secrets
      ansible.builtin.file:
        path: /etc/conduit
        state: directory
        mode: "0700"

    - name: Create the secrets once and never overwrite them
      ansible.builtin.copy:
        dest: /etc/conduit/conduit.env
        force: false
        mode: "0600"
        content: |
          APP_ENV=prod
          SECRET_KEY={{ lookup('ansible.builtin.password', '/dev/null', length=48, chars=['ascii_letters', 'digits']) }}
          JWT_SECRET_KEY={{ lookup('ansible.builtin.password', '/dev/null', length=48, chars=['ascii_letters', 'digits']) }}
          POSTGRES_HOST=127.0.0.1
          POSTGRES_PORT=5432
          POSTGRES_DB=conduit
          POSTGRES_USER=conduit
          POSTGRES_PASSWORD={{ lookup('ansible.builtin.password', '/dev/null', length=32, chars=['ascii_letters', 'digits']) }}
      no_log: true

    - name: Read the database password back from the server
      ansible.builtin.slurp:
        src: /etc/conduit/conduit.env
      register: secrets
      no_log: true

    - name: Create the database user
      community.postgresql.postgresql_user:
        name: conduit
        password: "{{ secrets.content | b64decode | regex_search('POSTGRES_PASSWORD=(.+)', '\\1') | first }}"
      become_user: postgres
      no_log: true

    - name: Create the database
      community.postgresql.postgresql_db:
        name: conduit
        owner: conduit
      become_user: postgres

    - name: Get the code of one exact commit
      ansible.builtin.git:
        repo: "{{ repo_url }}"
        dest: /opt/conduit/src
        version: "{{ revision }}"
        force: true
      register: code
      notify: Restart the API

    - name: Install the Python packages
      ansible.builtin.pip:
        requirements: /opt/conduit/src/backend/requirements.txt
        virtualenv: /opt/conduit/venv
        virtualenv_command: python3 -m venv
      notify: Restart the API

    - name: Install the service
      ansible.builtin.template:
        src: conduit.service.j2
        dest: /etc/systemd/system/conduit.service
        mode: "0644"
      notify: Restart the API

    - name: Start the API now and after every reboot
      ansible.builtin.systemd_service:
        name: conduit
        state: started
        enabled: true
        daemon_reload: true

    - name: Restart now if anything changed
      ansible.builtin.meta: flush_handlers

    - name: Check that the API answers
      ansible.builtin.uri:
        url: http://127.0.0.1:8000/api/health-check
      register: health
      retries: 30
      delay: 1
      until: health.status == 200

    - name: Show the running version
      ansible.builtin.debug:
        msg: "{{ health.json }}"

  handlers:
    - name: Restart the API
      ansible.builtin.systemd_service:
        name: conduit
        state: restarted
        daemon_reload: true
```

Read it task by task. Every task has a name that says what it does. Compare the names with what you typed in Mission 2.

> [!NOTE]
> A script says “do this, then this”. A playbook says “make it so”. If PostgreSQL is already installed, Ansible does not install it again. That is called **idempotent**: run it any number of times, and the server ends up in the same state.

> [!NOTE]
> In Mission 2 you typed a password, and it stayed in your history. Here the playbook makes random secrets on the server, once, in a file that only `root` can read. They are never in Git, never on your laptop, and `no_log` keeps them out of the output.

**7. Install Ansible on the laptop:**

```bash
source .venv/bin/activate
python -m pip install ansible-core
ansible-galaxy collection install community.postgresql
```

**8. Commit and push the branch**, so the server can download it:

```bash
git add backend/version.py deploy/
git commit -m "Deploy the API to my server with Ansible"
git push -u origin deploy/ansible
```

**9. Deploy your branch:**

```bash
ansible-playbook -i deploy/inventory.ini deploy/playbook.yml -e revision=deploy/ansible
```

Checkpoint: the last task shows a `revision` that equals `git rev-parse HEAD`, and the summary line says `failed=0`.

**10. Run it again:**

```bash
ansible-playbook -i deploy/inventory.ini deploy/playbook.yml -e revision=deploy/ansible
```

Checkpoint: `changed=0`. Nothing needed to change.

**11. Check it the way a user would**, from the laptop:

```bash
curl http://YOUR-IP:8000/api/health-check
```

No terminal is open on the server, and the API runs. Look at what the playbook built:

```bash
ssh azureuser@YOUR-IP
systemctl status conduit --no-pager
ps -o user,cmd -C uvicorn
cat /etc/conduit/conduit.env
exit
```

Checkpoint: the service is `active (running)`, the user is `conduit`, and `cat` says `Permission denied`: even you need `sudo` to read the secrets.

**12. Merge.** Open a pull request in your fork (check the base repository). Two green checks, then merge. The playbook is code: it was reviewed like everything else.

## Mission 4 · The robot deploys (30 minutes)

> [!NOTE]
> The robot must log in to your server. If you gave it your own key and it leaked, you would have to replace your key everywhere. A separate key can be removed from the server in one line, and nothing else breaks.

**1. Make a key for the robot** on the laptop, and add its public half to the server:

```bash
ssh-keygen -t ed25519 -N "" -C "github-actions-deploy" -f ~/.ssh/conduit_deploy
ssh-copy-id -f -i ~/.ssh/conduit_deploy.pub azureuser@YOUR-IP
ssh -i ~/.ssh/conduit_deploy -o IdentitiesOnly=yes azureuser@YOUR-IP whoami
```

Checkpoint: the last command answers `azureuser`.

**2. Give the private half to GitHub as a secret.** Show it:

```bash
cat ~/.ssh/conduit_deploy
```

In your fork open **Settings → Secrets and variables → Actions → New repository secret**. Name: `DEPLOY_SSH_KEY`. Value: the whole text, from `-----BEGIN` to `-----END` with both lines. Click **Add secret**.

> [!WARNING]
> It is the robot's key, not yours, and it goes only into the secret store. GitHub never shows a secret again, hides it in logs, and does not give it to pull requests from other people's forks.

**3. A branch on the laptop:**

```bash
git switch main
git pull
git switch -c ci/deploy
```

**4. Add a third job at the end of `.github/workflows/ci.yml`**, at the same indentation as `unit-tests`:

```yaml
  deploy:
    needs: [unit-tests, secret-scan]
    if: github.event_name == 'push'
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v7
      - uses: actions/setup-python@v7
        with:
          python-version: "3.12"
      - name: Install Ansible
        run: |
          pip install ansible-core
          ansible-galaxy collection install community.postgresql
      - name: Give the robot its key
        run: |
          mkdir -p ~/.ssh
          echo "$DEPLOY_SSH_KEY" > ~/.ssh/deploy_key
          chmod 600 ~/.ssh/deploy_key
        env:
          DEPLOY_SSH_KEY: ${{ secrets.DEPLOY_SSH_KEY }}
      - name: Deploy this commit to the server
        run: ansible-playbook -i deploy/inventory.ini deploy/playbook.yml --private-key ~/.ssh/deploy_key -e revision="$GITHUB_SHA"
```

Read it line by line:

- `needs` — the job waits for both checks. If one is red, nothing is deployed.
- `if` — only a push to `main` deploys. A pull request is only tested.
- `secrets.DEPLOY_SSH_KEY` — the robot's key, taken from the secret store and written to a file only for this run.
- The last step is the command you ran on the laptop, with the robot's key and the exact commit `$GITHUB_SHA`.

**5. Commit, push, open a pull request:**

```bash
git add .github/workflows/ci.yml
git commit -m "Deploy every green commit on main to my server"
git push -u origin ci/deploy
```

On the pull request, `deploy` shows as **skipped**. That is correct. Merge it.

**6. Watch the robot.** Open the **Actions** tab. On `main` the job `deploy` starts after the two checks. Open its log: the same Ansible tasks you saw on the laptop.

Checkpoint: from the laptop,

```bash
git switch main
git pull
git rev-parse HEAD
curl http://YOUR-IP:8000/api/health-check
```

shows the same SHA twice. From now on, every merge goes live by itself.

## Mission 5 · A bad release and a rollback (15 minutes)

**1. Make a typo that the tests do not see.** On a new branch, open `backend/conduit/api/routes/health_check.py` and change the last line from `return response` to `return respons`.

```bash
git switch -c release/tidy-health
```

```bash
python -m pytest tests/unit -q
git add backend/conduit/api/routes/health_check.py
git commit -m "Tidy the health check"
git push -u origin release/tidy-health
```

The unit tests pass. Open the pull request: two green checks. Merge it.

**2. Watch the deploy fail.** The job `deploy` retries the health check for 30 seconds and turns red. The `curl` now answers with an error. Production is down.

> [!NOTE]
> The unit tests never start the application, so they never call the health check. The last task of the playbook did. A green check proves only what the checks check.

**3. Roll back first.** In the **Actions** tab open the previous run on `main` that was green and click **Re-run all jobs**. It deploys its own commit again. Checkpoint: the `curl` answers with the previous SHA.

> [!NOTE]
> Users cannot work while you look for the bug. Bring back the version that worked, then fix calmly. Notice what the rollback had to do: fetch the old code again and check every library again, because the playbook overwrote the old version on the server. Keep this in mind for the next lesson.

**4. Fix `main` with a revert.** Open the merged pull request `release/tidy-health` and click **Revert**. Merge the new pull request. The robot deploys the fixed `main`. Checkpoint: the `curl` answers with the newest SHA.

## Bonus (if you finish early)

**A. Reboot proof.** Run `sudo reboot` on the server. Wait a minute and run the `curl` from the laptop again, without doing anything else.

**B. Take the robot's key away.** On the server, delete the line that ends in `github-actions-deploy` from `~/.ssh/authorized_keys`. Re-run the deploy job and watch it fail. Put the key back with the `ssh-copy-id` command from Mission 4.

**C. The pain list.** Write down three things that still depend on the server itself: something that must already be installed, something that must be the same on every server, something that could break a rollback.

## Troubleshooting

1. **`ssh` to the server hangs.** Check the address. If it still hangs, the network may block port 22; tell the instructor.
2. **`curl` to port 8000 hangs, but the API runs.** Port 8000 is not open in Azure (repeat the `az vm open-port` step), or the network blocks it. Check from the server itself: `ssh azureuser@YOUR-IP curl -s localhost:8000/api/health-check`.
3. **`address already in use` on port 8000.** The program from Mission 2 still runs. On the server: `pkill -u azureuser uvicorn`.
4. **Ansible: `Host key verification failed`.** `deploy/known_hosts` is missing or belongs to another address. Repeat Mission 3, step 4, and run Ansible from the repository folder.
5. **Ansible: `couldn't resolve module/action 'community.postgresql…'`.** Run `ansible-galaxy collection install community.postgresql`.
6. **The health check task fails after 30 retries.** On the server run `sudo journalctl -u conduit -n 30 --no-pager` and read the last error.
7. **The deploy job fails with `Permission denied (publickey)`.** The secret is not the robot's private key, or its public half is not on the server. Repeat Mission 4, steps 1 and 2; the secret must include the `BEGIN` and `END` lines.
8. **The deploy job fails with `error in libcrypto` or `invalid format`.** The secret lost its last line break. Paste the key again and press Enter once at the end.

## Commands for today

| Goal | Where | Command |
|---|---|---|
| Log in to the server | laptop | `ssh azureuser@YOUR-IP` |
| Leave the server | server | `exit` |
